# ТЗ-1: Backend Core & Database (Фундамент)

**Статус:** Черновик
**Дата:** 29.11.2025
**Приоритет:** Высокий (Блокирует остальные этапы)

## 1. Цель
Подготовить архитектуру базы данных и API к строгому разделению проектов на два типа: **Corporate** (Корпоративный углеродный след) и **Product** (Углеродный след продукта). Обеспечить валидацию данных на уровне бэкенда, чтобы исключить смешивание несовместимых шаблонов отчетов.

## 2. Текущие проблемы
1. Поле `project_type` в БД существует, но по умолчанию ставится `PRODUCT`.
2. Нет валидации соответствия выбранных шаблонов (Reports) типу проекта.
3. Структура `dataset` (JSONB) не типизирована и не имеет различий для разных типов проектов.

## 3. Технические требования

### 3.1. База данных (Prisma Schema)
Файл: `prisma/schema.prisma`

1.  **Enum `ProjectType`**: Убедиться, что он используется корректно.
    ```prisma
    enum ProjectType {
      PRODUCT
      CORPORATE
    }
    ```
2.  **Модель `Project`**:
    *   Убрать `@default(PRODUCT)` у поля `projectType`, сделать его обязательным при создании.
    *   Добавить (опционально) поле `datasetSchemaVersion` для версионирования структуры данных.

### 3.2. API Создания проекта (`POST /api/projects`)
Файл: `src/app/api/projects/route.ts`

1.  **Входные данные (DTO)**:
    *   Добавить обязательное поле `type: 'product' | 'corporate'`.
    *   Поле `template_codes` остается массивом строк.

2.  **Валидация**:
    *   Получить список всех шаблонов (через `getAllReportTemplates`).
    *   Для каждого выбранного шаблона проверить свойство `scope` (см. ТЗ-2, но пока можно использовать заглушку или хардкод проверку).
    *   **Правило:**
        *   Если `project.type === 'corporate'`, разрешены только шаблоны с `scope: 'corporate'` или `'both'`.
        *   Если `project.type === 'product'`, разрешены только шаблоны с `scope: 'product'` или `'both'`.
    *   Если найдено несоответствие -> вернуть 400 Bad Request.

3.  **Инициализация Dataset**:
    *   Вместо пустого объекта `{}` создавать "скелет" данных в зависимости от типа.
    *   **Corporate Skeleton:**
        ```json
        {
          "organization_info": {},
          "facilities": [],
          "subsidiaries": [],
          "reporting_period": {},
          "data_points": {} // Плоские поля из CSV
        }
        ```
    *   **Product Skeleton:**
        ```json
        {
          "product_info": {},
          "bom_items": [], // Bill of Materials
          "processes": [],
          "transport_stages": [],
          "data_points": {} // Плоские поля из CSV
        }
        ```

### 3.3. Миграция данных (Опционально)
*   Если в БД есть существующие проекты, написать скрипт миграции, который проставит им правильный `projectType` на основе выбранных в них шаблонов (если шаблон CBAM/ISO14067 -> Product, если CSRD -> Corporate).

## 4. Критерии приемки (DoD)
1.  Нельзя создать проект без указания `type`.
2.  API возвращает ошибку, если попытаться создать Product-проект с шаблоном CSRD.
3.  В БД новые проекты создаются с корректным `dataset`, содержащим базовую структуру (скелет).
