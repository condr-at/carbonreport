# CBAM Supplier Review Package — локальная проверка

Дата: 2026-10-11. Объём: RULES-01/FLOW-01/OUTPUT-01 для собственного supplier review profile. Изменяемые статусы остаются в [BACKLOG](../../planning/BACKLOG.md).

## Результат

Работает цепочка: новая организация в существующем QA-аккаунте → новый продукт → CBAM_DATA_PACKAGE → пять разделов данных → проверка → сохранённая версия → скачанный ZIP. Это техническая проверка подготовки данных; официальный operator emissions report, подача CBAM и клиентская приёмка не заявлены.

- [Точные сохранённые входы](input-dataset.json), [независимая проверка](verify-artifact.py), [результат проверки](artifact-verification.json).
- [Контракт профиля и первичные источники](../../regulatory-requirements/CBAM_SUPPLIER_PACKAGE_CONTRACT.md).
- [Предложения по дальнейшему флоу](FLOW_IMPROVEMENTS.md).

Все данные примера синтетические. Названный документ OPS-2026-Q3 — тестовая ссылка, реального документа и верификации нет. Пример не утверждён как нормативный golden case или образец, принимаемый клиентом.

## Реализация

34 поля, из них 23 безусловно обязательных; остальные включаются по роли, indirect treatment, default/mixed basis и verification statement либо остаются дополнительными. Данные хранятся в общем `Project.dataset`; legacy/чужие поля сохраняются. В локальную БД добавлены 28 новых определений полей через добавочный sync; 6 полей использованы из существующего каталога. Полный seed, миграции, публикация и отправка получателю не выполнялись.

GET/PATCH/ZIP проверяют доступ к проекту и отчёту. Запись требует OWNER/ADMIN/EDITOR и доступный для записи проект. ZIP строится на сервере, только из сохранённой ожидаемой версии и при отсутствии ошибок комплектности. Это не проверка истинности эмиссий/документов. Расчёты direct и indirect раздельны, без суммы обязательств или повторного добавления прекурсоров. Архив содержит только активные поля и разрешённые свойства вложенных записей; документы не скачиваются и не вкладываются.

## Проверка самого результата

Python `zipfile` независимо прочитал ZIP и проверил CRC, ровно пять ожидаемых файлов, v8 и идентификаторы, 29 активных полей, исходные значения, расчёты 30/6 и согласованность CSV/JSON. Нормализованный evidence совпадает с реестром. Неактивные `INACTIVE_DEFAULT_A/B`, `INACTIVE_TEST_VERSION` и текст `Unsaved conflict draft` отсутствуют во всех файлах. Скрипт не импортирует production renderer.

HTML открыт отдельно как файл получателя через локальный статический сервер. Осмотрены начало, расчёты и evidence; горизонтального переполнения при ширине 1620 px нет. [Начало](09-summary-top.png), [реестр](10-summary-evidence.png), [расчёты](11-summary-calculations.png). Сырой evidence/default JSON убран из читаемого HTML; машиночитаемые значения сохранены в JSON/CSV. Печатная пагинация и мобильный вариант не проверялись.

## Исправленные дефекты

1. Обычный PATCH dataset записывал только `data_points`, стирая остальные корневые разделы. Теперь сохраняется остальной объект; отдельная регрессия проверяет также отсутствие мутации исходного значения.
2. Во время проверки нового экспорта обнаружено попадание произвольных вложенных JSON-свойств и неактивных defaults. Нормализация ограничивает свойства и компоненты; регрессия проверяет отсутствие маркеров утечки во всех файлах ZIP.
3. Overview нового supplier-проекта направлял пользователя в общую таблицу. Следующее действие теперь открывает профильную форму; подписи различают coverage и готовность.
4. Create Organization и фоновый Profile использовали одинаковые `org-name/org-description`, из-за чего поля модального окна теряли корректные доступные имена. Новые ID уникальны.
5. В новой форме исправлены сохранение нескольких default sources, уникальные предлагаемые evidence ID после удаления строки, доступность reload восстановленного устаревшего черновика и блокировка редактирования на время загрузки.
