# Аутентификация, восстановление доступа и роли

Дата: 2026-10-11. **Статус: локальные проверки завершены; публикация и реальная reset-ссылка проверяются следующим шагом.** Единственный актуальный план работ — [BACKLOG, AUTH-01](../../planning/BACKLOG.md#auth-01--оставшиеся-проверки-доступа). Этот файл фиксирует доказательства и границы текущей проверки, а не отдельный план.

Вопрос проверки: может ли пользователь восстановить доступ и продолжить работу, сохранив данные и не оставив доступ по старым токенам, чужому приглашению или неподходящей роли.

Согласованное правило: неподтверждённый аккаунт может работать в собственном workspace и готовить отчёт. Принятие приглашения в другую организацию требует подтверждённого email. Уже принятые членства не блокируются задним числом. Приглашения создаются для существующих аккаунтов внутри приложения; письма с приглашениями не отправляются.

Локальная проверка использовала только синтетические данные и отдельную БД. [Результаты auth/roles](auth-role-results.json), [состояние приглашения без подтверждённого email](roles-invitation-needs-email-verification.png), [истёкший refresh](auth-expired-refresh-sign-in.png). Полный исходный ZIP и дополнительные скриншоты лежат в игнорируемой `.artifacts/auth-access-20261011`; они воспроизводятся runner.

В локальном браузере подтверждены: неверная и истёкшая reset-ссылка не меняют пароль; успешный reset создаёт новую сессию, старые access/refresh и старый пароль получают 401, использованная ссылка — 400; конкурентный reset завершается 200 и 400. Пять ролей читают supplier package; OWNER/ADMIN/EDITOR могут записывать, обе viewer-роли получают 403 без изменения версии данных. Только OWNER/ADMIN видят управление участниками; прямые попытки остальных ролей пригласить, изменить роль или удалить участника отклоняются. Для приглашений проверены создание, принятие и отказ через UI, отсутствие доступа до принятия, чужой аккаунт, другая организация, повтор и неподтверждённый email.

В код внесены исправления:

- Неверные/истёкшие JWT дают 400 для reset/verification и 401 для refresh. Ошибка сервера остаётся 500; потенциально действующие cookies при такой ошибке сохраняются.
- Reset атомарно сравнивает прежний password hash перед записью. Подписанный контекст текущего hash отзывает старые access/refresh; успешный reset выдаёт новые HttpOnly cookies. Миграция БД не нужна, но прежним сессиям без контекста потребуется однократный вход.
- Сервер больше не доверяет входному `x-user-id`; middleware удаляет присланные заголовки идентификации. SSR проверяет актуальную сессию и открывает вход при её отзыве.
- Добавлены восстановление через `/session`, один повтор своего API-запроса после refresh и проверка безопасного внутреннего redirect. Восстановление страницы и повтор сохранения подтверждены браузером.
- Logout дожидается начатого refresh, запрещает возобновление старых запросов и полностью открывает `/login`, очищая память интерфейса. Сфокусированный тест проверяет порядок установки/очистки cookies и отсутствие повторной мутации.
- Конкурентные операции принятия приглашения и изменения роли сериализуются в пределах организации; accept/decline атомарно меняют только PENDING. Восстановление удалённой организации снова доступно её владельцу.
- Появились действия принятия/отказа приглашения и понятный переход к подтверждению email. Управление участниками скрыто для ролей без прав; `Create invite` прямо сообщает об отсутствии письма. Права проверяются сервером.

Границы: локальные JWT и синтетические пользователи созданы только в отдельной PostgreSQL `*_e2e_test`; реальная отправка писем отключена. Это не доказательство доставки reset-письма. Cross-tab logout и серверный реестр сессий не реализованы: выход очищает cookies браузера, reset отзывает старый контекст. Роль verifier не означает готовность процесса согласования; выдача новых verifier-ролей остаётся выключенной. Проверки не подтверждают остальные форматы отчётов или нормативную приёмку.

Предложения по пользовательскому пути, ещё не заявленные реализованными:

- После подтверждения email возвращать пользователя к ожидающему приглашению, сохраняя безопасный внутренний адрес продолжения.
- При окончательном истечении сессии показывать явное действие повторного входа рядом с несохранённой формой; отдельно проверить сохранность черновика после возврата.
- При исчерпании мест объяснять, какая роль заняла лимит и какое действие доступно владельцу, сохраняя ожидающее приглашение для повторной попытки.
- Для viewer-ролей показывать состояние «только чтение» непосредственно в форме отчёта. Запрет записи подтверждён API, но доступные элементы редактирования всей формы в этом проходе отдельно не проверялись.
