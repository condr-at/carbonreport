# Нормативные требования и правила пользовательского маршрута

Дата первичного сбора: **2026-10-11**. Здесь требования разложены по каждому из **48 активных кодов** отчётов, с источниками, применимостью и открытыми вопросами. Это база для проектирования и проверки, а не гарантия соответствия продукта всем перечисленным режимам.

## Навигация

- [Каталог всех типов и карточек](../report-reference/CATALOG.md).
- `reports/<CODE>.md` — статус нормы/схемы, применимость, результат, входные данные, контрольные вопросы, проверка человеком и пробелы.
- `families/` — общая логика родственных отчётов и существенные изменения источников.
- [GAPS.md](GAPS.md) — расхождения текущего каталога и требований, недоступные материалы и непроверенные области.
- [RULE_MODEL.md](RULE_MODEL.md) — как превратить материал в вопросы, условные обязательные поля, проверки, сообщения об ошибках и E2E-кейсы.
- [Формат результата и свобода оформления](RULE_MODEL.md#формат-результата-и-допустимая-свобода-оформления) — как различать официальный бланк, гибкую вёрстку при обязательных раскрытиях, файл получателя и внутренний документ. Универсальный свободный PDF не предполагается.
- [Первичные источники](../report-reference/SOURCES.md) и [оригинальные образцы](../report-reference/README.md) хранятся в связанном реестре без повторного копирования общих файлов.

## Разные основания требований

| Категория | Что определяет требования |
| --- | --- |
| Регуляторный отчёт | Закон/акт, роль, юрисдикция, отчётный период, переходные положения и формат принимающего органа |
| Добровольный стандарт | Выбранная методика, редакция, договор с получателем и условия верификации |
| Рейтинг/схема | Текущий цикл и анкета владельца схемы; его оценку нельзя выдать самим |
| Клиентская форма | Конкретный файл/портал и инструкция заказчика, а не универсальный набор полей |
| Внутренний документ | Согласованная задача и критерии качества; он не становится обязательной государственной формой |

Внутри карточек нужно отличать подтверждённую норму, рекомендацию владельца стандарта и наше предложение по UX. Предлагаемые валидации пока не реализованы. Перед кодированием каждого правила нужны точный пункт/страница и проверенная трактовка — особенно если полный стандарт платный.

## Как не направить пользователя по неверному пути

Сначала определить страну, роль, период и желаемый результат. Затем выбрать редакцию и границы, после этого показывать применимые поля. При недостатке информации показывать «нужна проверка» с конкретным следующим действием. Нельзя по умолчанию заключать «вам обязательно нужен отчёт» либо «вы освобождены» по одному общему признаку.

Отдельно вести: данные собраны, расчёт выполнен, проверка ответственным пройдена, внешняя верификация получена, файл создан, документ подан и принят. Нынешний процент заполненных полей подтверждает только заполненность.

Изменения 2026 года, архивные формы и переходные правила отражены в карточках. Наличие новой редакции не отменяет автоматически все ранее выпущенные документы: применимость устанавливается по периоду и правилам перехода конкретной схемы.

## Что ещё нужно для нормативной реализации

По выбранному типу: получить недоступные исходные стандарты/формы, подтвердить методику и применимость, сопоставить требования с dataset, определить расчётные данные/коэффициенты и права их использования, реализовать проверки и проверить конечный файл. Затем пройти независимую проверку там, где она требуется схемой.

Состояние задач — [REF-01, RULES-01, OUTPUT-01 и REL-01 в BACKLOG](../planning/BACKLOG.md). Здесь нет второго журнала задач. Данные редактируются в `docs/report-reference/research/*.json`; карточки и сводки генерируются из них. Проверка новых редакций перед выпуском обязательна для конкретного результата; автоматический мониторинг сейчас не настроен.
